# Curse / QFG4 loading candidate — October 12, 2026

I confirmed music, speech and effects work in Curse with the previous SDL
zero-timeout fix. That fix and the earlier renderer/keyboard fixes remain in
this build. I also confirmed QFG4 DOS and Windows are playable, but startup
was slow. This is a new test candidate, not a public release: I have not yet
measured these new optimizations on my Wii U.

## Changes

- Curse/digital iMUSE: read reserved audio-index words sequentially instead
  of seeking four bytes for every entry. Newlib's relative-seek path invokes
  its input flush/seek logic; long music indexes can repeat this hundreds or
  thousands of times. Decoding, music transitions and audio buffer sizes are
  unchanged. This removes unnecessary seeks; it does not establish that all
  scene/menu delay came from this code.
- SCI/QFG4: cache the successful size query of each read-only volume held by
  the existing open-file cache. Resource bounds checks still run for every
  entry. Cache eviction/close discards the size; reopening queries it again.
  Failed size queries are retried. Save files and transient chunk/FSNode
  streams are unaffected. On Wii U the uncached query calls fstat, backed by
  WUT's FSAGetStatFile. No resource validation is skipped.
- Bounded, main-thread timing for SCUMM scene setup, engine pause/resume,
  original-menu thumbnail capture and menu restoration:
  only operations taking at least 50 ms are logged, up to 24 per game launch.
  Scene timing includes intentional fades; dialog interaction time is not
  measured. These markers do not cover every part of frame/menu rendering.
  Existing audio counters and SCI startup phase markers remain enabled.

The previous log does not measure the reported three-second transitions.
The earlier QFG4 diagnostic log measured about 156 seconds from resource init
to execution, with about 151 seconds spent in the second source scan. Actual
speedup needs a console comparison using the same SD, game files and settings.

## Install and test

1. Back up the executable, configuration and saves; retain the previous ZIP
   for rollback. Extract the entire Aroma ZIP to the SD root, replacing the
   existing executable. No INI changes or new game-file conversions are needed.
2. The startup log should identify **IO optimization candidate 20261012**.
   It still appends to **`SD:/scummvm/scummvm-compat-diagnostic.log`**.
3. In Curse, repeat the same scene changes and menu open/close operations.
   Report approximate delays before/after and whether the menu is the game's
   own menu or ScummVM's. Check speech, effects and uninterrupted music again.
4. Start QFG4 DOS and Windows from separate fresh application launches. Time
   Start to the intro/title, then play, save/load, and return to the launcher.
   Allow up to five minutes before treating startup as a hang; the result is
   still unmeasured on hardware. Preserve a log from each test.
5. Check repeated game return/reopen, keyboard confirm/cancel, and normal Quit.
   If stable, check another previously working game as a regression test.
6. After a real hang, avoid repeated resets. Once fully powered off, copy the
   log from the SD on the PC before relaunching. Flush/fsync cannot guarantee
   log survival or prevent SD corruption after a forced power-off.

Logging itself adds overhead. Local tests and cross-compilation are not Wii U
performance tests. Non-Aroma RPX remains experimental/unverified. No games,
ROMs, user configuration, saves or logs are bundled.

## Rebuild

With the prepared SDK active and the existing SDL patches installed:

```sh
bash backends/platform/sdl/wiiu/build-io-fix.sh
```

Default output: `../build-scummvm-wiiu-io-fix-20261012/`. Earlier packages are
preserved. The SDK is unchanged from the successful timer-fix candidate.

Host regression tests (actual changed C++ with mocked dependencies):

```sh
python3 backends/platform/sdl/wiiu/tests/io-fix/run.py
bash backends/platform/sdl/wiiu/tests/diagnostics/run.sh
```

These check table equivalence/seek counts, cached-size lifetime and failed
queries, bounds-validation behavior, and timing report limits. They do not
emulate SD latency or prove a three-second delay is fixed.
